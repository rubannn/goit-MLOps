# Прибирання інфраструктури ДЗ3/ДЗ4 (2026-08-28 → 2026-08-29)

Кластер `goit-mlops` (VPC + EKS + Argo CD + весь стек ДЗ4 — MLflow, MinIO, PostgreSQL, PushGateway, kube-prometheus-stack) простояв піднятим після тестування ДЗ4 і був знищений після завершення ДЗ5.

## Виконана послідовність команд

### 1. `terraform/argocd`

```bash
cd terraform/argocd
terraform plan -destroy      # Plan: 0 to add, 0 to change, 4 to destroy
terraform destroy -auto-approve
```

Впало з `Error: uninstallation completed with 1 error(s): uninstall: Failed to purge the release: release: not found` — 5 Application (`minio`, `postgres`, `mlflow`, `pushgateway`, `monitoring-stack`) коректно каскадно видалились разом з app-of-apps, але `application` та `infra-tools` зависли з finalizer `resources-finalizer.argocd.argoproj.io`, namespace `infra-tools` — `Terminating`.

Розблоковано вручну:

```bash
kubectl patch application application -n infra-tools -p '{"metadata":{"finalizers":null}}' --type=merge
kubectl patch application infra-tools -n infra-tools -p '{"metadata":{"finalizers":null}}' --type=merge
```

Namespace видалився сам. Синхронізовано Terraform state:

```bash
terraform state list
terraform state rm helm_release.argocd kubernetes_namespace.argocd
terraform state list   # лишились тільки data-джерела
```

### 2. `eks-vpc-cluster/eks`

```bash
cd ../../eks-vpc-cluster/eks
terraform plan -destroy      # Plan: 0 to add, 0 to change, 43 to destroy
terraform destroy -auto-approve
```

Впало з `Error: deleting EKS Cluster (goit-mlops): ... ResourceInUseException: Cluster has nodegroups attached` — попри те, що обидві відстежувані node group (`cpu-nodes`, `gpu-nodes`) щойно успішно видалились (`Destruction complete`).

Причина: **осиротіла дублююча node group** `cpu-nodes-20260828113839850500000001` (`m7i-flex.large`, `desiredSize: 2`), яка ніколи не потрапляла в Terraform state — залишок від завислого DynamoDB-лока під час переключення на `m7i-flex.large` кількома днями раніше. Ці 2 зайві інстанси тихо коштували гроші весь цей час.

Видалено вручну:

```bash
aws eks list-nodegroups --cluster-name goit-mlops --profile goit-terraform --region us-east-1
aws eks delete-nodegroup --cluster-name goit-mlops --nodegroup-name cpu-nodes-20260828113839850500000001 --profile goit-terraform --region us-east-1

# очікування завершення видалення (кілька хвилин)
aws eks describe-nodegroup --cluster-name goit-mlops --nodegroup-name cpu-nodes-20260828113839850500000001 --profile goit-terraform --region us-east-1 --query "nodegroup.status" --output text
# ... поки не ResourceNotFoundException
```

Після цього destroy кластера повторено успішно:

```bash
terraform destroy -auto-approve   # Destroy complete! Resources: 19 destroyed.
```

## Команди для перевірки, що AWS чистий

```bash
# EKS-кластери — має бути порожньо
aws eks list-clusters --region us-east-1 --profile goit-terraform

# Всі EC2-інстанси (включно з тими, що поза Terraform) — не має бути запущених нод/зайвих інстансів
aws ec2 describe-instances --region us-east-1 --profile goit-terraform \
  --filters "Name=instance-state-name,Values=running,pending" \
  --query "Reservations[].Instances[].{Id:InstanceId,Type:InstanceType,State:State.Name,Name:Tags[?Key=='Name']|[0].Value}" \
  --output table

# VPC — має лишитись тільки default VPC
aws ec2 describe-vpcs --region us-east-1 --profile goit-terraform \
  --query "Vpcs[].{Id:VpcId,IsDefault:IsDefault,CidrBlock:CidrBlock}" --output table

# NAT Gateway — не має бути жодного (платний ресурс, якщо забути видалити)
aws ec2 describe-nat-gateways --region us-east-1 --profile goit-terraform \
  --filter "Name=state,Values=available,pending" --output table

# Step Functions / Lambda (ДЗ5) — має бути порожньо
aws stepfunctions list-state-machines --region us-east-1 --profile goit-terraform
aws lambda list-functions --region us-east-1 --profile goit-terraform \
  --query "Functions[].FunctionName" --output json

# Elastic IP — не має бути жодної невикористаної (платна, якщо не прив'язана)
aws ec2 describe-addresses --region us-east-1 --profile goit-terraform --output table
```

Результат перевірки (2026-08-29): EKS — порожньо; EC2 — жодного запущеного інстанса; VPC — лишився тільки `default` (172.31.0.0/16); NAT Gateway — порожньо; Step Functions/Lambda — порожньо; Elastic IP — порожньо.

## Висновок / урок на майбутнє

Коли `terraform apply`/`destroy` переривається (Ctrl+C, завислий DynamoDB-лок) під час заміни ресурсу через `create_before_destroy` (зміна `instance_types` у managed node group завжди форсує replacement) — варто **завжди** звіряти `aws eks list-nodegroups` з `terraform state list` одразу після відновлення, а не покладатися лише на `terraform plan` (`No changes`), бо state може "забути" про реально існуючий дублікат, якщо новий ресурс встиг створитися в AWS до того, як apply впав.
